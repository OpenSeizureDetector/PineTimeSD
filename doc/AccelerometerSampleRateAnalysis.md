# Accelerometer sample rate analysis (125 samples in 4.3 s instead of 5.0 s)

**Firmware analysed:** PineTimeSD **v0.7** (`9ed594bb`, `project(pinetime VERSION 230.0.7)`) — current production release.
**Date:** 2026-10-03, updated 2026-10-05
**Related:** `Android_Pebble_SD` `SdDataSourceBLE2` (BLE2 data source), `doc/BleAdvertisingFailureAnalysis.md`, [Android_Pebble_SD issue #262](https://github.com/OpenSeizureDetector/Android_Pebble_SD/issues/262)

## 1. Summary / verdict

**This is a watch-firmware timing/parsing issue, not a phone-app issue and not ordinary accelerometer-chip ODR inaccuracy.**

**2026-10-05 update:** after the Phase 0 Part 2 transport fixes were committed as `6704ff13`, phone logs showed
approximately **120–123 samples/s** rather than 25 Hz. The Part 2 parser/transmission fixes were necessary but not
sufficient: the BMA423 initialization also had to disable the FIFO header, disable advanced power save for polled
FIFO reads, explicitly force the intended 25 Hz `ACC_CONF`, and verify the resulting registers. See §10 and
`doc/Phase0_Part3_AccelerometerConfigFixes.md`.

The BMA421/BMA425 output data rate is configured to 25 Hz (`src/drivers/Bma421.cpp:98`). The problem
is downstream of the sensor:

1. `Bma421::Process()` does not query the actual FIFO byte count before parsing; it reads a fixed 192 bytes and
   asks `bma4_extract_accel()` for up to 18 frames (`src/drivers/Bma421.cpp:93-94,136-140`).
2. `MotionService` **hard-caps every notification at 3 FIFO frames**, regardless of how many frames were
   actually extracted (`src/components/ble/MotionService.cpp:81-85`).
3. The notification cadence is the **SystemTask message-loop cadence**, which is not synchronised to the ODR
   and is not fixed (`src/systemtask/SystemTask.cpp:189,192`).

Therefore the sample rate delivered to the phone is

```
delivered_rate = min(nFifo, 3) x SystemTask_loop_rate
```

and **not** reliably 25 Hz. With the loop at its nominal 10.24 Hz this gives **30.7 samples/s**, so the phone's
125-sample buffer fills in **~4.1 s** instead of 5.0 s. The observed 4.3 s floor corresponds to a loop period of
~103 ms (9.69 Hz) — the nominal 97.66 ms plus per-iteration work. The arithmetic closes exactly (§4).

Issue #262 measured four watches against three phones: watch B was consistently ~4.98 s, while watches A, C and
D were consistently ~4.32-4.40 s, with little dependence on phone. That is the expected signature of this
firmware path: the delivered rate is set by each watch's FIFO parse result and SystemTask cadence, not by the
phone. It is **not** evidence that the BMA421 ODR register is 16% inaccurate.

Watches that show the expected 5.0 s are either in the correct-parse regime, where `nFifo` is the true frame
count and the callback sends 2 or 3 frames as available, or their loop happens to run at ~8.33 Hz, which is
exactly `25 Hz / 3 frames`.

### What you are actually receiving (see §5 for the derivation)

On a 4.3 s watch, per 125-sample burst:

| | count |
| --- | --- |
| Samples generated by a true 25 Hz sensor during the burst | **~107.5-108.8** |
| Samples stored by the phone | **125** |
| Extra samples beyond the 25 Hz conservation budget | **~16.2-17.5** (~13-14 %) |
| Real samples lost | **0** (while the loop stays faster than 8.33 Hz) |

The extra samples must come from the firmware's fixed 192-byte FIFO over-read/over-parse. They are **not simple
duplicates of the preceding datapoint**: full-event analysis of event 1174667 found no cross-burst overlap
(§5.3). The original prediction that they would always decode to a fixed `0x80,0x00` filler constant was **not
observed** in that event, so the filler bytes may instead contain stale or otherwise non-fresh FIFO-buffer
contents. Live logging of `bma4_get_fifo_length()`, returned `nFifo`, and transmitted payload length is still
needed to classify the surplus byte-for-byte.

The important consequence is unchanged: 125 samples collected in ~4.3 s are presented to the algorithm as 5 s at
25 Hz, stretching the frequency axis by roughly **+16 %**.

## 4. The arithmetic

| Quantity | Value | Source |
| --- | --- | --- |
| Loop wait | `xQueueReceive(systemTasksMsgQueue, &msg, 100)` = 100 ticks | `SystemTask.cpp:192` |
| Tick rate | `configTICK_RATE_HZ = 1024` | `src/FreeRTOSConfig.h:62` |
| Nominal loop period / rate | 100/1024 = **97.66 ms → 10.24 Hz** | derived |
| `Process()` calls | one per loop iteration | `SystemTask.cpp:189` |
| Accel ODR | 25 Hz | `Bma421.cpp:98` |
| Frames accumulated per iteration | 25 × 0.09766 = **2.44** | derived |
| Frames transmitted per iteration | **`min(nFifo, 3)`** | `MotionService.cpp:81-85` |
| FIFO read length | `sizeof(fifo)` = 32×3×2 = **192 bytes**, fixed | `Bma421.cpp:93-94` |
| Extraction request cap | **18 frames** | `Bma421.cpp:139` |

Two regimes:

**Regime A — empty-FIFO marker detected correctly.** `nFifo` equals the true new-frame count (≤ 3 at this
cadence), so the `nData < 3` branch sends exactly `nFifo` frames. Every real sample is transmitted, the rate is
exactly 25 Hz, and 125 samples take **exactly 5.000 s**.

**Regime B — empty-FIFO marker not detected.** The parser over-runs into bytes beyond the valid FIFO contents and
returns the full 18-frame request, so the `else` branch fires and sends exactly 3 frames per iteration. The phone
stores 125 samples but drops one tail sample per burst (§7), so it must receive 126 samples:

| Loop rate | Delivered rate | Phone period for 125 stored samples |
| --- | --- | --- |
| 10.24 Hz (nominal idle) | 3 × 10.24 = **30.72 Hz** | 126 / 30.72 = **4.10 s** |
| 9.69 Hz (nominal + ~5 ms work) | **29.07 Hz** | 126 / 29.07 = **4.33 s** ← observed ~4.3 s |
| 9.55 Hz | **28.65 Hz** | **4.40 s** ← issue #262 watch C |
| 8.33 Hz | **25.00 Hz** | **5.04 s** ← knife-edge case |

Note the design has **zero margin**: 2.44 frames accumulate per iteration against a cap of 3, and 8.33 Hz is the
knife edge above which samples start being dropped.

### Why the marker detection fails

`Bma421::Process()` never asks the sensor how much data is present. `bma4_get_fifo_length()` is not called, and
this driver's `bma4_read_fifo_data()` does not call it either — it reads a fixed `fifo->length` bytes
(`bma4.c:2407-2445`):

```c
reset_fifo_data_structure(fifo);
rslt = bma4_read_regs(addr, fifo->data, fifo->length, dev);   // 192 bytes, always
```

The Bosch v2.x contract is that the **caller** sets `fifo->length` from `bma4_get_fifo_length()` first.
PineTimeSD leaves it at 192 permanently, so the parse terminates only on the empty-FIFO heuristic:

```c
// bma4.c:4047-4059
if ((fifo->data[*data_index]     == BMA4_FIFO_MSB_CONFIG_CHECK) &&   // 0x80  (bma4_defs.h:464)
    (fifo->data[*data_index + 1] == BMA4_FIFO_LSB_CONFIG_CHECK))     // 0x00  (bma4_defs.h:463)
    *data_index = fifo->length;    // stop parsing
```

This is data-dependent in **both** directions:

- If the chip's response beyond valid data is not exactly `0x80, 0x00` at a 6-byte-aligned boundary (e.g. all
  `0x80`), the check never fires → filler is parsed as samples → `nFifo` inflates to the 18-frame request cap →
  **Regime B**.
- If a *genuine* sample has `X_lsb = 0x80, X_msb = 0x00` (12-bit value +8 ≈ 0.008 g), the check fires early →
  the parse is truncated → **real samples lost → period > 5 s**.

Note the parse order in `bma4_extract_accel` (`bma4.c:2471-2479`): a frame is unpacked **first**, then the next
position is tested. So when the marker is genuine, no extra frame is produced — Regime A is exact.

## 5. What is really being received?

### Conservation argument

The firmware configures the sensor for 25 Hz. A 4.3 s burst stores 125 samples, so the phone's stored rate is
`125 / 4.3 ≈ 29.1 samples/s`. The Android buffer-full path drops exactly one further sample per burst (§7), so
the watch actually delivered about `126 / 4.3 ≈ 29.3 samples/s`. If the ODR really is 25 Hz, the surplus is
approximately:

```
29.3 - 25.0 ≈ 4.3 samples/s
```

or about **18 extra samples per 125-sample burst (≈14 %)**. Those samples cannot be fresh 25 Hz sensor samples.

### Full-event evidence: event 1174667

Event `1174667` from `/home/graham/osd/osdb/osdb_3min_allSeizures.json` was extracted to
`/tmp/opencode/event.json` and analysed with `/tmp/opencode/analyze_event.py`:

| Property | Result |
| --- | --- |
| `dataSourceName` | `BLE2` |
| `watchSdVersion` | `230.0.7` |
| `sampleFreq` reported by phone | 25 |
| datapoints | 41 |
| first / last datapoint | `2026-04-22T18:20:48Z` / `2026-04-22T18:23:42Z` |
| interval counts | 26 × 4 s + 14 × 5 s |
| average interval | **4.35 s** |
| stored samples | 41 × 125 = **5125** |
| stored rate over 174 s | **29.45 samples/s** |
| estimated received rate including one Android drop per burst | `(5125 + 41) / 174 = 29.69 samples/s` |
| `rawData` / `rawData3D` length consistency | all 125 / 375 |
| magnitude consistency with x/y/z | all datapoints consistent |
| cross-boundary prefix matches ≥10 samples | **0 / 40** |
| immediate cross-boundary duplicate | only `dp4 -> dp5` |
| adjacent exact 3D duplicates | 265 / 5084 = 5.2 % |
| periodic lag-3 or mod-3 duplicate signature | none |
| predicted `0x80,0x00` filler magnitudes ≈27.7 or ≈7067 | **0 occurrences** |
| magnitude range | 241.8 to 3822.2 binary milli-g |

This rules out two simple explanations:

1. **The datapoints are not rolling/overlapping copies of one another.** There is no significant cross-boundary
   alignment, so Android is not storing the same 125-sample window repeatedly.
2. **The surplus is not the originally predicted fixed filler constant.** No ≈27.7 or ≈7067 magnitudes appear.
   The over-read bytes may instead decode stale local FIFO-buffer contents, sensor over-read data, or another
   non-fresh pattern. The conservation deficit is nevertheless real.

Live firmware logging is therefore still required to identify the exact source of the extra samples. The
decisive quantities are `bma4_get_fifo_length()`, the returned `nFifo`, and the payload length actually appended
by `MotionService::OnStepCountRequested()`.

### Consequences for seizure detection

1. **Frequency axis error of roughly +16 %.** `SdAlgOsd.java:26,89-97` and `SdAlgFlap.java:24,86-93` hard-code
   `mSampleFreq = 25`, and `SdDataSourceBLE2.java:1284` hard-codes `mSdData.mSampleFreq = 25`. With a delivered
   rate of ~29 Hz, every FFT bin mapping is wrong by ~16%: a real 3 Hz tremor is interpreted as ~3.5 Hz, and the
   alarm bands (`mAlarmFreqMin/Max`, `mFreqCutoff`) examine the wrong part of the spectrum.
2. **Non-uniform sampling.** If extra samples are inserted only when fewer than three fresh frames are present,
   their spacing is irregular. This can act like amplitude modulation and broaden spectral peaks.
3. **Silent sample loss in the other direction.** Whenever the loop slows below 8.33 Hz, more than three frames
   may accumulate but only three are transmitted; frames beyond the third are discarded, giving periods > 5 s.
4. **Android tail loss.** The phone discards one sample from the final notification of every burst (§7). This
   makes the period slightly longer, not shorter, and is not the cause of the 4.3 s bursts.

## 6. Watch-to-watch evidence

### Issue #262 four-watch / three-phone test

Issue #262 measured the time to collect 125 samples on four PineTime watches and three phones, all using
PineTimeSD v0.7 (`230.0.7`) and phone app 5.0.8:

| Watch | Description | Mean 125-sample period | Implied stored rate |
| --- | --- | ---: | ---: |
| A | old OSD development watch | 4.333 s | 28.85 Hz |
| B | Benjamin's production watch | 4.983 s | 25.08 Hz |
| C | spare caravan watch | 4.393 s | 28.45 Hz |
| D | new June 2026 batch watch | 4.320 s | 28.94 Hz |

The per-watch standard deviations were small, and each watch gave essentially the same result on all three
phones. That matches the firmware path:

```
stored_rate ≈ 3 frames/notification x notification_rate - Android tail-drop correction
```

For watches A, C and D, the implied notification rate is about 9.55-9.72 Hz, i.e. a 103-105 ms SystemTask
iteration. Watch B is consistent with either correct variable-length notifications at the true 25 Hz ODR, or a
loop cadence near the 8.33 Hz knife-edge where `3 frames x 8.33 Hz = 25 Hz`.

### Most likely explanation for the slow watch

The 25 Hz sensor and ~10 Hz SystemTask loop produce an average of only 2.44 new frames per FIFO read, while
`MotionService` transmits `min(nFifo, 3)` frames. Watch B therefore behaves like **Regime A**: the parser sees
the true frame count (usually 2 or 3), variable 12/18-byte notifications are sent, and the average is the real
25 Hz. Watches A, C and D behave like **Regime B**: the fixed 192-byte read/parse over-runs, `nFifo` reaches the
request cap, and the notification path sends exactly 3 frames on every ~103-105 ms iteration, giving
28.45-28.94 Hz.

The repeatability across phones points at watch-local hardware/runtime behaviour rather than Android or BLE
scheduling. The likely watch-dependent factors are:

- BMA421 versus BMA425 chip variants and their different config files
  (`src/drivers/Bma421_C/bma423.c:1010-1013`; System Info screen 2 shows `Accel.` type);
- bytes returned beyond the valid FIFO contents — whether they match the driver's `0x80,0x00` empty-frame
  heuristic or are parsed as stale/invalid samples;
- I²C/TWI timing, clock stretching, pull-ups, bus capacitance, or the duration of the fixed 192-byte FIFO read;
- contention on the shared TWI bus, particularly with always-on heart-rate measurement;
- silent TWI write failures: `user_i2c_write()` returns `BMA4_OK` regardless of the `TwiMaster` result
  (`src/drivers/Bma421.cpp:16-20`), so an unsuccessful `ACC_CONF`/FIFO-config write would not be detected.

This is **not** well explained by a claimed ±16 % BMA421 ODR tolerance. The extracted BMA423 datasheet does not
document such an ODR tolerance, and sensor time increments with a 39.0625 µs resolution. The observed ~15 %
spread is stable per watch and matches the two firmware parse/transmit regimes much better than ordinary
chip-to-chip ODR variation. Firmware-side register readback and FIFO logging are still needed for proof.

### Definitive watch comparison

On one fast watch (A/C/D) and the slow watch (B), record:

1. System Info screen 2 → `Accel.` type (`BMA421` or `BMA425`).
2. Read back `ACC_CONF` (`0x40`), `FIFO_DOWNS` (`0x45`) and `FIFO_CONFIG_1` (`0x49`) after `Init()`.
3. Log, for each `Process()` call: `bma4_get_fifo_length()`, returned `nFifo`, payload bytes appended by
   `MotionService`, and `xTaskGetTickCount()` loop delta.
4. Apply `patches/phase0-part2-accelerometer.patch` and retest. If the fast watches become ~5.0 s with variable
   12/18-byte notifications, the parse regime is confirmed. If they remain ~4.3 s while reporting a genuine
   `nFifo` sum of ~29 frames/s, the cause is actual ODR/config/timebase rather than over-parsing.

## 7. Other defects found on the same path

Firmware:

- `MotionController.cpp:44-46` — `fifo[nFifo-3]`, `fifo[nFifo-2]`, `fifo[nFifo-1]` with **no bounds check**.
  For `nFifo < 3` this is a negative index (`uint16_t` wraps to 65533 when `nFifo == 0`). `Process()` also
  returns `{}` with `fifo == nullptr` when `isOk` is false (`Bma421.cpp:123-124`) → **null-pointer dereference**.
- `MotionController.cpp:49-51` — the "only notify when values changed" guard is commented out, so
  `OnNewMotionValues(fifo, 0)` fires and sends **zero-length notifications**, wasting mbufs from a 12-block pool.
- `MotionService.cpp:126` — `ble_gattc_notify()` return code ignored → congested/failed notifications silently
  drop samples.
- `MotionService.cpp:101-108` — `OnNewStepCountValue()` allocates an mbuf **before** the connection-handle check
  and returns without freeing it → **mbuf leak**. With `MSYS_1_BLOCK_COUNT = 12` and `BLE_HS_FLOW_CTRL = 0`
  (`syscfg.h:57-58, 585-586`) this feeds directly into the host-reset scenario in
  `doc/BleAdvertisingFailureAnalysis.md`.
- `MotionService.cpp:118` — `this->data` is a raw pointer into `Bma421::fifo`, dereferenced by the access
  callback which the **NimBLE host task** can also invoke on a phone-initiated read → data race with SystemTask.
  Entries beyond `nFifo` are never cleared, so they hold stale data from previous reads.
- `Bma421.cpp:139` — `nFifo = 18` caps extraction at 18 frames although the buffer holds 32 and 192 bytes were
  already read out of the sensor; frames beyond 18 are **permanently discarded**. The comment on that line
  ("Should be about 20 (200 Hz ODR / 10 Hz main loop)") is stale — the ODR is 25 Hz.
- `SystemTask.cpp:426-436` — `UpdateMotion()` returns early during `GoingToSleep`/`WakingUp`, and during
  `Sleeping` unless raise-wrist/shake/motion-subscribed → sample gaps around sleep transitions.

Phone (`SdDataSourceBLE2.java`):

- `:1284` — `mSdData.mSampleFreq = 25` hard-coded (see §5 consequence 1).
- `:1241-1310` — the buffer-full branch is **inside** the per-sample loop. For the PineTime 3D format each
  notification contains 3 samples. Because `125 mod 3 = 2`, 41 notifications store 123 samples; the 42nd
  notification stores samples 124 and 125, then its third sample enters the `else` branch. That third sample is
  never stored, and the copy loop at `:1276` reuses/clobbers the outer loop variable `i`, so the outer loop
  exits immediately. **Exactly one sample from the final notification is dropped per burst.** Triplet alignment
  survives because the whole remaining notification is discarded and `nRawData` is reset, but this is still a
  real sample-loss bug.
- The dropped tail sample makes bursts slightly **longer**, not shorter: the watch must deliver 126 samples for
  the phone to store 125. It cannot explain the observed 4.2-4.4 s periods.
- `nRawData` is reset **only** at `:1299` — never on connect/reconnect, so the first burst after a reconnect can
  be short.
- No sample timestamps, so the app cannot detect or correct a rate error.

## 8. Recommendations

Firmware (root fix, in priority order):

1. **Use `bma4_get_fifo_length()` before reading.** Set `fifo_frame.length` to the reported byte count rounded
   down to a multiple of 6 and clamped to `sizeof(fifo)` (`Bma421.cpp:136-140`). This eliminates the fixed
   192-byte over-read, makes `nFifo` the true extracted-frame count, and prevents both over-parse and
   false-truncation by the `0x80,0x00` heuristic.
2. **Send all valid extracted frames.** Replace `3 * 3 * sizeof(int16_t)` with `nData * 3 * sizeof(int16_t)`
   (`MotionService.cpp:81-85`), bounded by buffer size and the negotiated MTU. Better still, build the mbuf
   directly and use `ble_gattc_notify_custom` (the commented-out lines at `MotionService.cpp:117,125`) instead
   of the raw-pointer/access-callback indirection — that removes the data race and the stale-pointer risk at the
   same time.
3. **Raise the extraction request** from 18 to the 32-frame buffer capacity, or loop until the FIFO reports
   empty, so no frames are silently discarded.
4. **Add temporary firmware logging** of actual FIFO byte count, returned `nFifo`, appended payload length, and
   loop period on one fast watch and one slow watch. This will identify why watches A/C/D sit at ~4.3 s while
   watch B sits at ~5.0 s.
5. **Bounds-check `nFifo`** in `MotionController::Update` and guard `fifo == nullptr`; skip the x/y/z read and
   the notify when `nFifo == 0`.
6. **Check the notify return code** and count failures; fix the mbuf leak in `OnNewStepCountValue` by moving the
   allocation after the connection-handle check.
7. **Report the real delivered sample rate or ODR to the phone** (e.g. extend the OSD status/manufacturer
   characteristics, or add a new characteristic) so the app stops hard-coding 25 Hz.
8. Optional: move motion sampling onto a fixed-rate FreeRTOS timer/task so the cadence is deterministic instead
   of message-loop dependent.

Phone (defensive + diagnostic):

9. **Measure the true rate** — count samples and elapsed time between bursts, set
   `mSdData.mSampleFreq` from the measurement, log it, and feed it to the FFT instead of the hard-coded 25.
10. Reset `nRawData = 0` on connect and after service discovery.
11. Move the buffer-full processing out of the per-sample loop, or carry the remaining samples from the current
    notification into the next buffer, so the final sample is not dropped. Also use a separate variable in the
    copy loop at `SdDataSourceBLE2.java:1276` so it cannot clobber the outer sample-loop index.
12. Add diagnostics: samples per notification, notifications per second, payload byte lengths, and a count of
    repeated/constant values.

## 10. Follow-up after Phase 0 Part 2: ~120 Hz instead of 25 Hz

Commit `6704ff13` contains the Part 2 FIFO parser and BLE transmission fixes. A subsequent phone log showed
payload sizes of 66, 72 and 84 bytes. `SdDataSourceBLE2` logs `numSamples` as **bytes**, so those are 11, 12 and
14 3D samples. With notifications roughly every 100–102 ms, the delivered rate was about **120–123 samples/s**.

Part 2 removed the fixed 192-byte over-read and the 3-frame notification cap, but it still relied on sensor state
that `Bma421::Init()` did not enforce:

| Remaining defect | Why it matters |
| --- | --- |
| `FIFO_CONFIG_1` reset value enables `BMA4_FIFO_HEADER` (`0x10`) | Part 2 parses fixed 6-byte headerless frames; header mode changes frame size/alignment. |
| `bma423_write_config_file()` leaves advanced power save enabled | The BMA423 datasheet requires APS disabled for polled FIFO reads without a watermark interrupt. |
| `ACC_CONF` reset value `0xA8` is 100 Hz | The intended 25 Hz value is `0xA6`; if the vendor write does not latch, the FIFO fills ~4× too fast. |
| Vendor `bma4_set_accel_config()` may use a stale `perf_mode_status` delay | The 25 Hz register write can occur before the chip is in the expected power/performance state. |
| `FIFO_DOWNS` was not explicitly forced | The intended filtered/no-downsample mode should be written and not merely assumed from reset state. |
| TWI failures were silently converted to success | A failed `ACC_CONF`, FIFO-config, length-register or FIFO-data transaction could be treated as valid data. |

The implemented follow-up is `patches/phase0-part3-bma423-configuration.patch`, documented in
`doc/Phase0_Part3_AccelerometerConfigFixes.md`. As a deliberate Stage 1, it keeps the OEM
`bma4_set_accel_config()` call and changes only one variable at a time. It:

1. disables advanced power save after config-file upload,
2. explicitly configures filtered FIFO data, downsample factor 0, no sensor-time frames, disabled header and enabled accelerometer FIFO,
3. writes `ACC_CONF`/`ACC_RANGE` with the OEM helper, then enables the accelerometer last,
4. reads back `ACC_CONF`, FIFO config, `FIFO_DOWNS` and advanced power save, and refuses to mark the sensor OK on mismatch,
5. propagates `TwiMaster::ErrorCodes::TransactionFailed` through `Bma421::Read()`/`Write()` into `BMA4_E_COM_FAIL`,
6. checks `bma4_get_fifo_length()` and `bma4_read_fifo_data()` return codes in `Process()`.

If the readback proves the OEM call does not latch 25 Hz, the fallback is a manual low-power-delayed
`ACC_CONF`/`ACC_RANGE` write with identical byte composition (see `doc/Phase0_Part3_AccelerometerConfigFixes.md` §8).

Expected result after the follow-up: normal MTU-23 notifications of 12 or 18 bytes, payload sizes always multiples
of 6 bytes, total delivered rate ~25 samples/s, and a 125-sample phone burst of ~5.0 s. If initialization fails
its readback, the firmware now produces no motion samples rather than streaming invalid data.
